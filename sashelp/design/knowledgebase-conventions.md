# 知识库写作约定

本文约定知识条目的内容标准：写什么、怎么核实、怎么组织、怎么引用。版式与发布由站点构建流程负责，不在本文讨论。

## 1. 选题

适合收进知识库的题目，通常同时满足：

- 是实际工作中反复被问到的问题，而不是教科书式的概念罗列；
- 有相对明确的答案，或至少有可操作的判断路径；
- 能落到权威依据（标准原文、法规、厂商文档、官方示例）；
- 答案对做项目的人有直接帮助：能改代码、能改数据集、能避免一次返工。

不适合的题目：纯个人偏好、没有来源的经验之谈、只能回答"看情况"而没有判断依据的问题。

## 2. 核实

- 优先查原始文档：CDISC 的 IG / 实施指南、FDA / CDE 的技术指南、SAS 官方文档、产品手册。
- 写清楚版本：SDTMIG 3.2 与 3.3 的结论可能不同，ADaMIG、SAS 版本同理。
- 文档之间冲突时，以发布日期更新、层级更高的为准，并在正文里说明冲突点。
- 引用示例数据集的结论时，先确认示例本身是不是标准要求（示例文档不是标准）。
- 拿不准的地方宁可写"这里没有强制规定，常见做法是……"，不要编一个确定结论。

## 3. 结构

一条知识按固定顺序组织：

1. **结论先行**：开头两三句话直接回答"能不能 / 该不该 / 用哪个"，不要先铺垫背景。
2. **说明与依据**：解释为什么，必要时给出判断分支。
3. **判断路径**：有分支时用流程图或表格，把"什么情况走哪条路"列清楚。
4. **示例**：需要动手时给最小可运行示例，并给出运行结果。
5. **参考出处**：列出用到的原始文档与章节。

篇幅控制：一件事讲透即可，不把相邻主题塞进同一篇；确实相关时在末尾加"相关条目"链接，而不是大段复述。

## 4. 写作风格

- 像当面跟同事解释：先说结论，再说原因，少用"其归属是""由此推出""该规则确立了"这类书面套话。
- 句子短，一段一个意思；能用主动句就不用被动句。
- 行业通用缩写直接用：SDTM、ADaM、SAFFL、ORRES、null flavor，不做中英对照，也不在每个词后面加括号注释。
- 不堆砌限定词。确实有例外时，把例外单独写成一段，而不是在主句里塞满"一般情况下、通常、可能"。
- 不确定的地方明确标注不确定，不要用模糊措辞掩盖。

## 5. 术语与格式

- 变量名、数据集名、选项名用大写并加代码格式，例如 `--ORRES`、`ADSL`、`DDFM=KR`。
- 日期、时间按 ISO 8601 写；涉及不完整日期时说明允许的精度。
- 标准名称写全称加版本，例如 "SDTMIG 3.3"，不要只写 "IG"。
- 中文与英文、数字之间不留空格；标点用中文全角，代码与变量名内部保持原样。

## 6. 示例

- 示例要能直接运行：自带数据、自带逻辑库、不依赖本机路径。
- 只保留说明问题所需的最少代码，不要贴一整段生产程序。
- 每个示例给出实际运行结果（日志关键行或结果表），并说明结果说明了什么。
- 示例里的数据要能体现结论：如果结论是"某情形不允许"，示例就要把这个情形构造出来。

## 7. 参考出处

- 每条知识末尾必须有"参考出处"。
- 每条出处写清：文档名称、版本、章节或页码、可访问链接。
- 引用网页时优先给官方稳定链接，不要给搜索结果页或转载页。
- 正文里的关键结论要与出处一一对应，读者能顺藤摸瓜查到原文。

## 8. 常见问题

- **只给结论不给依据**：读者无法判断结论是否还适用于自己的版本。
- **把示例当标准**：示例数据集、示例程序只是演示，不构成符合性要求。
- **版本混用**：把 3.2 的要求写成通用要求，或把新版本的放宽当成一直如此。
- **过度概括**：把"某个域的做法"写成"SDTM 的通用规则"。
- **中英混排堆括号**：一个词后面跟三四种叫法，反而增加阅读负担。
- **把站点操作写进正文**：文件命名、页面结构、构建命令属于发布流程，不写进知识条目。

## 9. 交付前检查

- [ ] 结论在第一段就能看到，且明确回答被问的问题
- [ ] 关键结论都能对应到参考出处的具体章节
- [ ] 版本、适用范围、例外情况写清楚
- [ ] 有分支时给出了判断路径（流程图或表格）
- [ ] 示例可独立运行，并附实际结果
- [ ] 文风口语化，无套话、无过度括号注释
- [ ] 参考出处齐全，链接指向官方原文
- [ ] 通篇没有与站点设计、文件布局相关的内容
