知识库 / ADaM

population flags 应该放在哪，如何递交？

放 ADaM 的 ADSL（subject 级），别放 SDTM 或 SUPPDM；人工判定的结果做成随包递交的支持性源数据集（比如 ADPRE）。

结论

人群标志（safety、ITT、FAS、PP、completers、randomized……）是分析决策的产物，不是采集到的事实，所以它的位置是 ADaM 的 ADSL，不该进 SDTM 的任何域（SUPPDM 也不行）。这一点从 SDTMIG v3.3 起就是硬要求，不是“建议”了。

先分清两件不相干的事

维度本场景答案说明
取值来源人工判定，非程序衍生影响 define.xml 的 Origin/Method 怎么写、QC 怎么做、文档要哪些
变量放在哪ADaM 的 ADSL由变量语义决定：它说的是“这个受试者属于哪个分析人群”，是分析属性
是不是 SDTM 意义上的“采集数据”不是SDTM 的 collected 指试验中对受试者的观察/干预/事件；统计分析的决定不是采集

所以记住两点：“人工给的”不等于“能放 SDTM”；“ADSL 里的标志”不等于“必须能由 SDTM 算法推出来”。ADaM 允许非算法来源，但必须文档化、能追溯。

版本是怎么演变的（这个很关键）

版本对人群标志的态度
SDTMIG ≤ 3.2允许作为 SUPPDM 的补充限定符；附录列了标准 QNAM：COMPLT、FULLSET、ITT、PPROT、SAFETY
SDTMIG 3.3DM 的 assumptions 改成“人群标志的补充限定符不应使用”，上面那些 QNAM 从附录撤掉
SDTMIG 3.4进一步明确：COMPLT、FULLSET、ITT、PPROT、SAFETY 这类人群标志不该出现在 SDTM 数据里

原因不只是“放错地方”，而是循环溯源：如果 SDTM 里有个 SAFFL，ADSL 里也有个 SAFFL，审评员就没法判断是标志驱动了分析，还是分析反推了标志。SDTM 的本职是忠实记录采集事实，人群归属是 SAP 做的决定。

数据是怎么流的

人群标志从头到尾不碰 SDTM

在 ADaM 里怎么写才对

  • 位置：ADSL，一人一条，subject 级。
  • 命名：字符型以 FL 结尾，数值型以 FN 结尾（比如 SAFFL/SAFFN）。
  • 取值：subject 级的字符标志只允许 Y/N，不许空；数值型用 1/0。
  • 数量：用于分析的数据集至少得有一个人群对应的标志；SAP 里定义的每个人群都要有标志。
  • 层级：如果是在参数级或记录级做子集，才用 --PFL/--RFL（这两类允许空值，只标 Y）。
  • 追溯：标志的推导规则写进 ADRG / define.xml，能追回 SDTM 的 DS（随机化、筛选失败）、EX（是否给药）、LB/VS（是否有基线）这些记录。

遗留场景：项目还在用旧版 IG

这是遗留场景，不是推荐做法。写法是 SUPPDM，subject 级的补充限定符：

  • RDOMAIN = "DM"，IDVAR = "USUBJID"，IDVARVAL 留空（DM 一人一条）。
  • QNAM 用 8 字符以内的名字（SAFFL、ITTFL、PPROTFL）。
  • QLABEL 不超过 40 字符；QVAL = "Y"/"N"。
  • QORIG = "DERIVED"，QEVAL = "SPONSOR"。

就算这么写了，也要在 cSDRG 里说明“这些标志在 ADSL 里也有、以 ADaM 为准”，不然容易被质疑两边不一致。

四种常见的错误放法

  • 在 DM 里加新变量：DM 结构固定，不允许新增非标准变量——这是 SDTM 的硬规则。
  • 用 DS 记录人群归属：DS 只放 disposition event 和 protocol milestone（随机化、筛选失败属于 milestone），人群归属不是处置事件。
  • 在 LB/VS/AE 的每条记录上都重复一个 SAFFL：冗余、不规范，还容易同一个受试者取值不一致；ADaM 用 merge 就能解决。
  • 放进 RELREC 或自定义域：绕一圈还是没解决“分析变量不该出现在 SDTM”这个根本问题。

人工判定清单怎么处理

当标志不是程序按规则算出来的，而是统计师在数据审核会上定的、用 Excel 给你，那就应该在 ADSL 制作阶段把这个外部文件导进来，再据此赋值。这完全符合标准。一步一步这么做：

  1. 文件规范：跟统计师约定固定模板——STUDYID、USUBJID、各人群标志（Y/N）、判定日期、判定人、依据/备注；文件级带版本号、生效日期、批准签字。
  2. 受控导入：原始 Excel 存进只读原始区，记下 MD5 和时间戳；程序只读不改，禁止手工改数。
  3. 技术校验：键唯一；USUBJID 跟 DM 完全对得上；取值只含 Y/N 且无空；覆盖率完整；跟 SDTM 做一致性交叉核对（比如 SAFFL=Y 应该有 EX 暴露记录）。对不上的只出清单回统计师确认，不许用程序结果覆盖人工判定。
  4. 合并赋值：拿 ADSL 骨架（DM 受试者全集）当主表，按 STUDYID + USUBJID 左连接；生成字符 SAFFL/ITTFL/PPROTFL，需要的话再加数值 SAFFN；没覆盖到的受试者默认怎么填（通常 N）要事先说好，因为 subject 级标志不允许空。
  5. 元数据追溯：define.xml 里，纯人工给定的用 Assigned，Comment 写明来源文件名、版本、日期、判定会议和合并键；如果还叠加了程序规则，就用 Derived 写清 Method。ADRG 里说明这个外部文件的角色、版本控制和 QC。
  6. 下游传播：其他 ADaM 数据集只从 ADSL 合并，别再各自去读 Excel，避免版本漂移。
  7. 版本与变更：清单版本跟 SAP、数据截止、锁库状态绑定；出新版先做影响评估，再重跑 ADSL 和全部下游；保留历史版本和变更日志；交付包内所有产物同一版本。
  8. 归档：原始清单、导入日志、QC 记录、会议纪要引用一起归档，让文件、数据集、元数据这三层都能追。

“程序可复现”的三条路

路线做法定位
A（首选）把判定规则算法化，人工会议只确认规则和例外（SAFFL 由 EX 推导、ITTFL 由 DS 随机化推导、PPS 由方案偏离规则推导）ADSL = SDTM + 随包程序就能复现
B（须人工判定时）把判定结果写成 ADaM 中间数据集随包交（比如 ADPRE），逐受试者记录每条判定标准和理由，用 SRCDOM/SRCSEQ 指回 SDTM 记录把分析判定在 ADaM 层结构化
C（坚持不交文件）只能做到“内部能复现 + 审评能解释”，不能声称满足“审评方自己衍生出一致 ADSL”，得在 pre-NDA 沟通时达成一致需 define.xml/ADRG 写清来源，声明留存备查

不管走哪条路，复现的工程措施都得做：输入冻结——导入后马上固化成受控的 CSV/SAS 数据集，记下版本、MD5、行数；确定性导入加断言——列类型显式指定，键唯一、取值合法、覆盖完整，任何一条断言失败就中止；程序自包含——相对路径、别调外部宏、单个 driver 端到端跑通；QC 证据——独立双编程或独立重算，再 proc compare 全量比对；版本绑定——清单版本跟 SAP/锁库绑定，出新版就触发全链路重跑。

标准要求和行业做法分开看

事项标准 / 监管要求行业常见做法（非强制）
标志位置ADSL；必要时 BDS/OCCDS 的 *PFL/*RFL在 ADSL 程序里统一读外部清单
不进 SDTM/SUPPDMSDTMIG v3.3 起明确在 mapping spec 和 SOP 里写明禁止
命名与取值FL/FN 结尾；Y/N；subject 级非空；至少一个人群标志同时输出字符和数值两套
元数据ADSL 及其元数据必须交；来源与推导能追溯Assigned/Derived + 文件名、版本、MD5 写进 define 和 ADRG
外部清单本身不要求作为数据集随申报交作为支持性文档归档，必要时提供审评
一致性核对没强制规定具体规则SAFFL↔EX、ITTFL↔随机化等交叉 QC
